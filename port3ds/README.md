# New 3DS port (experimental)

The goal is to run the recompiled game on a real New 3DS, locally, with no streaming. This folder holds the 3DS host and the build files. Nothing here comes from the game: the build is made on your computer from your own disc, and its output must stay private (see [CONTRIBUTING.md](../CONTRIBUTING.md)).

On a New 3DS with automatic picture skipping, the game clock holds about 60 game frames/s (median 502 ms per 30 frames) in the school lobby and the first battle. Per 600 game frames the screen showed 72 new pictures in the lobby and 127 in the battle (2026-11-22; it was 35 and 68 before the texture upload fixes below). The lockers last measured 59.9 game frames/s with 49 pictures per 600. The PS2 game clock targets 59.94 Hz. See [Status](#status) for scene coverage and limitations.

## What it needs
- A Mac or Linux PC with Docker (or OrbStack). The build uses the official `devkitpro/devkitarm` image.
- The patched `ps2-web-recomp` folder next to this repository, with the game translated into `generated/p3fes` (see [docs/install.md](../docs/install.md)), and `tools/ps2run_3ds_patch.py` applied.
- A New 3DS, New 3DS XL or New 2DS XL. An original 3DS or 2DS will not work: 64 MB of application memory is not enough.

## Build
```bash
python3 ../fes-pc-recomp-main/tools/ps2run_3ds_patch.py
```
Run that once, in the `ps2-web-recomp` folder. Then, from this repository:
```bash
port3ds/build.sh
```
Before the first build, compile the vector unit programs you recorded (see [Testing](#testing)), or set `VU=0` to leave them in the interpreter:
```bash
build/tools/vurecomp games/p3fes/vu1 generated/p3fes-vu3ds --scalar
```
Translate the game once more with the list of functions the 3DS runs natively. This changes only the 3DS build, because each call is inside `#ifdef __3DS__`:
```bash
build/tools/eerecomp games/p3fes/disc/SLUS_216.21 --entries games/p3fes/entries.txt --natives ../fes-pc-recomp-main/port3ds/natives.txt --out generated/p3fes
```
Run both in the `ps2-web-recomp` folder.

The result is `ps2-web-recomp/build/3ds/p3fes.3dsx`.

Optionally, add hot copies of the busiest game functions (about 6 to 8% fewer cycles on the game's core, see [What is left](#what-is-left), item 3). `tools/p3fes_eehot.py` writes them from the translated code and a profile of what ran. Its first lines list the four steps. The copies and profiles come from your copy of the game, so keep them private.

Optionally, mark the game code that never ran as cold, so GCC compiles it smaller and puts it after the code that does run:
1. Translate with `--record-seen` added to the `eerecomp` command above, then build.
2. Run a few scenes, each with a `frames N` test. Each run leaves `sdmc:/p3fes/eeseen.bin`.
3. Copy each file to `games/p3fes/seen/`.
4. Translate again, with `--seen FILE` once per file in place of `--record-seen`, then build.

The recording build is about 3 MB larger, which leaves the console about 1 MB of free memory. The recordings come from your copy of the game, so keep them private.

## Put it on an SD card
```bash
python3 tools/p3fes_3ds_sd.py "path/to/disc.iso" ../ps2-web-recomp -o /Volumes/YOUR_CARD
```
This needs about 4.7 GB free. It copies the programs and your disc, splits the disc into parts because FAT32 stops at 4 GB, and checks the parts against the original. If it stops, run it again: finished parts are kept.

| File | What it is |
| --- | --- |
| `/3ds/p3fes.3dsx` | The game. Start it from the Homebrew Launcher. |
| `/3ds/p3fes-probe.3dsx` | A small test that shows the memory and speed this console really gives. |
| `/p3fes/SLUS_216.21` | The boot program from your disc. |
| `/p3fes/disc.00`, `disc.01`, ... | Your disc in parts. A single `/p3fes/disc.iso` also works where the card allows it. |
| `/p3fes/movies/` | Optional: the movies at the top screen's size, see [Made for the console](#made-for-the-console). |
| `/p3fes/slot1.state` to `slot3.state` | States saved from the bottom screen. |
| `/p3fes/args.txt` | Optional test settings, one per line. See the top of `main3ds.cpp`. |
| `/p3fes/log.txt` | Everything the runtime prints. |
| `/p3fes/perf.txt` | One line of timing every 30 game frames. |

If the game crashes on a console with Luma3DS, the crash report is in `/luma/dumps/arm11`.

## Made for the console
Added on 2026-11-13. All of it is checked in Azahar. **None of it has run on a console yet**, so there are no console timings for it.

**Movies at the top screen's size.** The game's own movies are 640 wide, and decoding them through the translated game code took about 70 ms per game frame on the console. Now the build plays its own copy of each movie:
```bash
python3 tools/p3fes_3ds_movies.py make "path/to/disc.iso" -o movies
python3 tools/p3fes_3ds_sd.py "path/to/disc.iso" ../ps2-web-recomp -o /Volumes/YOUR_CARD --no-disc --movies movies
```
The first command needs ffmpeg and takes about two minutes. It writes 43 files, 240 MB in all. `p3fes_3ds_link.py movies movies` sends them over the network instead of the second command.
- `NN.p3v` is one movie at 400x240, as MPEG-1 video with a key picture every 15 pictures and no B pictures. `port3ds/mpeg1.cpp` decodes it on core 2, which a movie leaves idle, and `port3ds/movie3ds.cpp` converts each picture to a 16-bit texture and shows it. A 640x368 movie fills the screen; a 640x448 one is stretched to it, as the game's own picture is.
- `movies.cut` is what the game gets in place of each movie's video. For every video sector of the disc it says what to hand over instead: a timing movie with the original width and picture count, only 16 pixels high. The game decodes one row of macroblocks per picture. Each picture is followed by zero bytes up to the size of a full-height black picture, because the game's player starts a movie, and keeps it going, only while enough video data waits in its buffer. Without them the title movie (`P3CTOP2`) stopped after 10 pictures: the sound buffer filled, disc reads stopped, and the screen froze while the game ran on at full speed. The game skips the zeros on its way to the next start code. Sound sectors, sector positions and time stamps are the disc's own, so the game's player keeps its timing, its sound and its skip button. The disc on the card is not changed: `main3ds.cpp` swaps the sectors as they are read. A video sector with nothing in it becomes a padding packet. Filled with zero bytes instead, the game's reader walked through them four bytes at a time, 80 million reads in one movie.
- The two are kept in step by a marker. The top row of each black picture carries 32 black or white blocks: a fixed pattern, the movie's number, the picture's number and two check bits. The game converts each picture to RGB just before it shows it. The IPU asks `movie::watch` about every macroblock of that conversion, the marker is read there, and the picture with that number goes up. The build also reads earlier `P3CUT1` timing files with full-height pictures. To upgrade an existing set, run the movie maker with `--no-video` and replace `movies.cut` alongside the existing `.p3v` files.
- While a movie of ours plays, the conversion is left out and the game's picture comes out black every time, so the drawing side has no new texture to decode.
- On the Mac build with a patched copy of the disc image, the opening movie made 6,436 conversions against 6,434 with the disc's own video, and the IPU's block decodes fell from 3.4 million to 32,000. In Azahar a cold boot showed the title movie from the copies, in step with the game's own at the same frames, and reached frame 13,980 in 240 s against 4,080 before.
- A state saved in the middle of one of the game's own movies does not carry on after this: the decoder is handed the black movie in the middle of a picture group. `movies 0` in `args.txt` gives such a state the disc's movie.
- `tests/test_3ds_movies.py` builds a made-up movie, cuts it and checks the markers, the untouched sound sectors and the decoder against ffmpeg (70 dB at worst).

**Drawing at 400x240.** A PS2 picture wider than the top screen was drawn into a 512x256 texture and scaled down to the screen. It is now drawn at 400x240 inside that texture and goes up texel for texel. That is 27% fewer pixels to fill, and no blur from the scaling.

**Stereo picture.** With the 3D slider up, each full-size target can allocate a separate 512×256 texture and depth surface for the right eye. Every batch is drawn twice, with a sideways shift worked out from its depth in the vertex shader (`eye` in `gs.v.pica`). Shapes drawn without a real depth test (menus, text, fades) do not shift, so they sit on the screen's surface, and the scene lies behind it. The farthest things are 10 pixels apart between the eyes at the slider's top. `stereo N` in `args.txt` or the bottom screen's 3D DEPTH buttons set the strength, 0 to 10, 5 to begin with; 0 shows the same picture to both eyes. Nearly all of a scene's corners fall in the far three sixteenths of the depth range (`debug 8` logs the spread), so that is where the shift is spent. Azahar's shots of the two eyes in the lobby and the dorm show the characters shifted and the panels still. Drawing twice costs GPU time, and the picture skipping pays for it; how much is not measured. Movies are flat.

**Bottom screen.** SAVE STATE and LOAD STATE with three slots, L3 and R3, FAST (lets a light scene run faster than the PS2), 3D DEPTH, and the game frames per second. A state is written packed with zlib's fastest setting as it is made, about 11 MB instead of 46 MB, because a whole one does not fit the heap; the old file is replaced only once the new one is whole. Loading reads packed and plain states alike. LOAD STATE restarts the program with the state, which takes the 12 seconds or so of any restart. In Azahar a state saved in the lockers scene loaded and carried on with the same picture as the run it came from. The buttons themselves were not pressed there, and how long a save takes on the console's card is not measured.

## Wireless test link
While the game runs it listens on port 5577 of the console, and `tools/p3fes_3ds_link.py` works from any computer on the same network: `status`, `fetch <folder>` (logs, crash reports, screenshots), `press a 4`, `shots 30`, `draw 1`, `quit`, `run`, `settings "load lobby.state;stats 1"` and `install`. The address it tries first is in the tool; change it with `--host`. `install` sends the program zlib-packed (42 MB becomes 16 MB), and the game keeps reading for up to 10 ms each vblank while a file arrives. On the console a packed install now takes about 50 to 60 seconds; a build from before packing answers the packed request with an error, and the tool then sends it plain. Each upload leaves a line in `log.txt` with the time spent receiving, unpacking, writing and waiting.

After the first packed install, the link stopped answering, while the game kept running for over two hours. Packed uploads were reaching the card in pieces of about 5 KB, and the card writes small pieces slowly: 41.7 of 44 seconds went to writing, and the file arrived at 79 KB/s, slower than plain. The Mac gave up after five minutes, but the game then kept waiting on that connection, so no new one got through. Writes now go through a 128 KB buffer: a packed 46 MB saved state went over in 27 seconds, and plain uploads went from 370 to 826 KB/s. The game now drops a connection that is quiet for 20 seconds during a transfer, or for two minutes between commands. It opens a new listener when the old one fails, and it writes connections, drops and finished uploads to `log.txt`. `install` waits 60 seconds for the console instead of five minutes. While a file arrives, the I/O processor thread on core 1 slows the console's network service: plain uploads went from 217 to 368 KB/s with `iopthread 0`.

**The link has no password, on purpose: anyone on your network can replace the game while it runs.** It can write only `/3ds/p3fes.3dsx` and `/p3fes/args.txt`. A new program must start like a 3DSX and match its checksum, and the old one stays as `/3ds/p3fes.3dsx.bak`. It refuses to read the disc, the boot program, saved states and Luma's backups. `link 0` in `args.txt` turns it off. Don't run it on a network you don't trust.

The first build with this link has to get there another way. Without moving the card, press Y in the Homebrew Menu on the console, then run `3dslink` from the devkitARM image:
```bash
docker run --rm -v "$PWD/build/3ds:/b" devkitpro/devkitarm:20260610 /opt/devkitpro/tools/bin/3dslink -a 192.168.1.133 /b/p3fes.3dsx
```
Run it in the `ps2-web-recomp` folder. It replaces `/3ds/p3fes.3dsx` and starts it.

## Limits found so far
| Limit | Number | What it means |
| --- | --- | --- |
| Translated game code and vector programs for the ARM11 | 43.4 MB | Fits. Measured with `-O2`, which ran faster on the console than the smaller `-Os` (91 against 102 ms per game frame). Each new vector program adds to this. |
| Code region of a 3DS program | about 63 MB | The 32 MB of PS2 RAM cannot sit in the program's data, so it lives at a fixed heap address right after the 28 MB heap (`0x09C00000`, which fits an ARM immediate, so a guest address takes one `add`). If the heap size changes, this address must change with it. A real console refused the PS2 RAM at `0x0B000000` and `0x0C000000` with `0xE0E01BFD`, and Azahar allows both. |
| Application memory | 124 MB | 48.4 MiB program + 32 MiB PS2 RAM + 28 MiB heap + 13 MiB linear heap = 121.4 MiB, confirmed on the console, so about 2.6 MiB is left. Going over stops the game at start-up, so more vector programs than that will need the heap cut. The heap has about 6 MB spare in the lobby: a queue doubling in size stopped the game once, so the queues between the threads now have fixed sizes. The linear heap holds textures, and the cache keeps it nearly full. After the menus its free space is in pieces, so a big texture needs older ones thrown out until a large enough piece appears. |
| Azahar CPU speed | 268 MHz clock | Azahar does not implement the New 3DS speed switch, so its timing does not match a real console. |

## Status
Checked in Azahar 2126.2 (New 3DS mode):
- The game boots from the split disc parts on two threads and runs from a cold start through the logos, title, menus and well into the opening movie (about 15,500 game frames) with no crash or hang, and the movie shows. That run stopped at its time limit, still in the movie.
- Saved states from the Mac build load. These were compared side by side with the Mac build's picture, with no crash and no missing texture: name entry, the dorm lounge, hallways and stairs, the player's room, shoe lockers, school lobby, assembly hall (54,000 triangles), school gate, dialogue with portraits, the Dark Hour scenes, the Velvet Room, the rooftop battle with its menus, and the level-up screens.
- The rooftop battle was also played live on this build from the end of the awakening movie, with button presses: the fight, the command menu, Results, level-up, and the talk with Yukari afterwards. That was about 5,000 game frames on the final build. Only shots every 30 frames were looked at.
- One open fault: a small black square appeared on the text box in 1 of 11 3DS shots of the level-up screens, with skipping on, and in none of 151 Mac shots. The cause is not known.
- Sound plays through NDSP on core 1 (`audio3ds.cpp`, `sound 0` turns it off).

How it runs: the game runs on one core and the I/O processor on core 1, which the system shares (`iopthread 0` in `args.txt` puts it back on the game's core, in exact lockstep). The vector programs, the GIF and all drawing run on the New 3DS's second application core (core 2, or core 1 if that cannot be had; `vuthread 0` in `args.txt` keeps everything on one core). Between them is a 7 MB queue, big enough for a whole picture to wait while the one before it is drawn. The game thread follows the VIF's registers itself, so it never waits for a result.

On a New 3DS, `splitgs 1` runs the renderer on core 0 at a lower priority than the game. `splitgs 2` shares core 1 with the I/O processor. This lets core 2 run the next vector program while the renderer consumes the previous one's graphics packets. Both modes support automatic and fixed picture skipping. The VU and renderer apply the skip decision when each reaches the picture boundary in its queue. The split worker uses a 1.5 MiB queue and a 512 KiB stack. The renderer stays on the VU core by default, with software rendering, or when the VU cannot run on core 2. Change `splitgs` and restart to switch modes.

Automatic picture skipping uses queue waits and the game clock. It checks elapsed time every 32 pictures. The first step draws two of three pictures, the next one of two, then one of three and so on. When skipped pictures save game-thread work and the game is still behind, it can draw as little as one picture in nine. It tries drawing more again when timing recovers. Their register changes and absolute uploads still happen, and only vector programs that have run before are left out, so the next picture finds the same state. Uploads to the double buffer are left out too, because only those left-out programs would read them, and the game thread filters them before they reach the queue. That rests on that data being used once: lobby pictures still match with it on, but the first battle has only been checked by a few shots, and other scenes not at all. A program not seen before still runs in a skipped picture, with drawing turned off. Many scenes swap between two frame buffers, and a fixed skip would always draw into the same one, leaving the one on show frozen, so while skipping, the buffer just drawn is shown instead. Some scenes also blend the last picture into the next, so an odd run of skipped pictures alternates one fewer and one more: that averages the same and draws into each buffer in turn. Without it the stale buffer showed through as noise. `draw N` in `args.txt` sets a fixed rate, and `draw 1` draws everything.

The skip also goes up when the game falls behind its vblank budget for reasons other than drawing (up to one picture in seven). If drawing fewer pictures did not bring the time per round down by 3%, the skip goes back and stays for 16 rounds. A lower skip is tried in a short round of 8 pictures and taken back at once if those ran more than 6% late; each failed try doubles the on-time rounds before the next one (3 up to 48), each good one halves them. Before this the skip was lowered after every 3 rounds on time, and in the lobby walk the game then fell behind for a whole round about every 4.5 seconds (30-frame windows of 535 to 690 ms, sound tempo down to 66%); now the same walk holds 500 ms with the highest window 540, and shows 13 to 15 pictures a second instead of 7 to 11. `debug 1024` logs each decision as a `[pace]` line. On the console (2026-11-22) this took the lockers from 70% of full speed at about 13 pictures a second to 99 to 100% at about 11; the lobby (6.4 pictures a second) and the battle (18 to 20) stayed at full speed.

Sound follows the game's speed. When the game makes sound slower than real time, `audio3ds.cpp` stretches it in time (WSOLA: 10 ms steps, the best overlap within 5 ms found by correlation, a sin² cross-fade), so it plays slower at the same pitch instead of breaking up. The stretch tempo goes from 100% when more than 80 ms is queued down to 35% at 42 ms. Every 5 seconds the log has two lines: `[3ds] game at X% of full speed`, with pictures a second, the share of time the game waited for the queue (`ee blocked`) and the share the VU thread was idle; and `[audio] X% of real time made`, with dropped samples, underruns, the mean and lowest tempo, and how much is queued.

Movies log `[movie] movie N (NAME, sectors ...) from its 3DS copy` once each, or `has no 3DS copy`. A `movies.cut` from before 2026-11-22 holds full-height black pictures (`P3CUT1`), which the game decodes in full: on the console the title movie ran at 43% of full speed with one, and at 100% and 30 pictures a second with a current one.

| 2D screen, 40 to 90 shapes | about 17 ms | about 10 ms |
| Menu, about 590 shapes | not measured | about 30 ms |

Per picture (two game frames) in the lobby with everything drawn, the drawing core is busy for all of the 584 ms: vector programs about 350, GIF and shape collection 85, VIF about 110, uploads 40. The game code itself only runs for about 2 million of the 9.8 million EE cycles in a picture; the rest is idle and costs nothing.

With one picture in four drawn, the game core is now the limit: about 284 ms per picture, of which the I/O processor is about 45 and DMA about 50 (mostly copying the vector data into the queue and walking it). The "game" figure in the log subtracts the drawing core's time as well, so it reads low when the cores overlap. Translated code alone comes to an estimated 16 million ARM instructions per picture, or about 60 ms. The rest of that time is spread thinly, with no single large cause left.

How a movie picture is made: the IPU decodes one macroblock at a time, and the game's own code does motion compensation and adds the two together. About 780 macroblocks make one picture. The IPU decoder takes about 50 ms of the 234 ms per picture. Twenty routines from the game's video code and C library run natively (`native3ds.cpp`, listed in `natives.txt`). Nineteen of them were compared with the game's code on every call for about 2,000 movie frames, with no difference. The other is `memcpy`.

A real New 3DS runs at 804 MHz but does not finish one instruction every cycle, so Azahar's times do not convert to the console's. The hardware floats rely on the FPU's start-up mode (flush denormals, round toward zero), which has not been read back from a console, and pictures from the console match Azahar's with it.

Accuracy given up for speed, on the 3DS build only: EE and VU0 floats use the FPU, so the last bit of a result can differ from the bit-exact code, EE floats and the common VU0 float operations no longer clamp infinities and invalid values on the way in or out (rounding toward zero already stops overflow reaching infinity), and vector programs skip the PS2's overflow and denormal handling. The IPU uses an integer IDCT and leaves out the mismatch toggle: in testing 0.8% of samples differed, by at most 1, and a movie frame stayed within 3 levels out of 255 of the exact decoder's picture. Vector programs not compiled yet still run in the interpreter: a few calls per picture in the Dark Hour scenes, about 15 in battle.

How the renderer works: `pica.cpp` replaces `raster::draw`. Shapes collect in a batch until a GS setting changes. Each PS2 frame buffer gets a render target of its true size, up to 512x256, and the shapes drawn with a texture that was rendered earlier use that target. The PICA has no palettes, so textures are decoded into a cache, keyed by a hash of the bytes uploaded for them, because this game moves the same textures around GS memory every frame.

Three things the GS does need care on this GPU:
- **Alpha test with a fail action.** Nearly all models here keep colour but not depth for pixels that fail the alpha test. The GPU cannot split a pixel, so such a batch is drawn twice, once per kind of pixel. Before this, the clear parts of models wrote depth and hid what came later: that was the black patch near the bench and the hard edges round the battle's pools. This adds GPU work that Azahar does not charge for.
- **Fog.** The GS mixes towards a colour by a value that comes with each vertex. That value reaches the third texture stage as a coordinate into a small ramp texture.
- **Blending by destination alpha** works because alpha is doubled on the way in, so 0x80 is stored as 1.0.

Not done in the renderer: the destination alpha test, dithering, mipmaps, region wrap modes, render-to-texture at an offset, and copies from the frame buffer.

## What is left
1. **Test on real hardware.** It runs on a New 3DS from the Homebrew Menu. A cold start ran for 37 minutes (34,700 game frames) with no crash report. Per game frame the console gives: level-up screens 13 ms of work, held to 16.7, first battle 22 ms, lockers 32 ms, lobby 45 ms with automatic skipping (one picture in five, one every 0.4 s), 36 ms at one in twelve, movies about 71 ms, which beats Azahar's clock. With every picture drawn, the lobby's pixels stay within rounding of Azahar's. Installing and restarting over the wireless link work there, a restart takes about 12 seconds. The lobby matches Azahar with every picture drawn: the first shot after loading is black in both, because the game is fading in. One lobby shot taken with skipping on was also black, cause unknown; none of 11 shots in a live fight were.
2. **More speed.** The vector programs are real work: moving registers into local variables gained 1%. With pictures skipped the game core is the limit, and the console's own counters now show where its time goes. Add `pmu A B` to `args.txt` and each `perf.txt` line gets that core's cycles, two hardware events (0 instruction cache misses, 1 and 2 stalls on instructions and data, 8 instructions, 11 and 13 data read and write misses, 18 load and store queue full) and the time the game waited for the I/O processor and the time that processor worked. Splitting the counts by activity for 30 frames of the lobby at `draw 12` showed the sampling profile used before had been far off: transfers took 43% of the core, not 18%.

| Activity, millions per 30 frames | Cycles before | Cycles now | Instructions now |
| --- | --- | --- | --- |
| Game code and everything else | 546 | 552 | 171 |
| VIF channel | 334 | 218 | 78 |
| Texture channel | 129 | 38 | 8 |
| Other DMA | 39 | 40 | 7 |
| Events and kernel | 24 | 24 | 7 |

   Three things were wrong with the transfers. This game names most of its data in one DMA tag and sends it with the next, and a command split that way fell back to the path that copied everything, twice. Everything kept was copied again through a buffer. And each transfer posted its own message to the queue. Now the double-buffer data of a skipped picture is dropped even when split, what is kept is written in place into one long message, and the long data of an unpack, and textures of 4 KB or more, go as an address for the drawing core to read from PS2 memory. The game can change that memory first: in the lobby 40% of the addressed unpack data had changed by then (none of the textures), because bone matrices live in a buffer the game rewrites. That reaches only a skipped picture, and only as newer values in VU memory, which the next drawn picture sets again. Commands are always copied, so both sides read the same stream. Copying the commands costs about 25 million cycles of the saving. An earlier version sent whole runs of commands as addresses, and those changed too, so leave it this way.

   On the console, ms per game frame in the lobby went from 50 to 42 at `draw 12` and from 64 to 45 with automatic skipping, and the level-up screen from 29 to 20. What is left of the VIF channel is about 5,600 transfers per picture at about 900 instructions each, spread evenly over parsing, DMA tags and the queue. Memory barriers are not it: the store buffer drains only 0.2 million times, and building without thread-safe statics changed nothing. Waiting for the I/O processor is about 180 ms of each 30 frames, and polling instead of sleeping does not help, because it really is behind. It runs the music sequencer and the ADX mixer in an interpreter, flat across many routines (the largest, a sample doubling loop at 0x4A5B8, is about 9%), at about 600,000 instructions per vblank and 19 ms of core 1, so hand ports will not fix it. That also puts a floor of about 19 ms under every scene, and the level-up screen is now at it. A predecoded interpreter is the clearest saving left. Build with `PROF=1` for the detailed timers, which cost speed. Decoding video on the idle drawing core would need the game's whole picture loop replaced, because the game asks the IPU for one piece at a time.
   The I/O processor was next, and it was the limit on every light scene: about 600,000 instructions per vblank at about 25 cycles each in the interpreter. It runs the sound driver, and only about 7,500 instructions of that run in any one scene. `tools/p3fes_iopgen.py` turns the code that ran into C++, one function per block, each jumping straight to the next. The work per 30 frames on the level-up screen fell from about 450 ms to 170, and the time the game spends waiting for it from about 240 ms to 60.

   Since the level-up screen now beats a PS2, the game holds itself to 59.94 game frames per second. `uncapped 1` in `args.txt` takes that off, for measuring. The lobby's game core is now busy all the time, so what limits it is back to item 3, and movies are still limited by decoding.

Second, `eerecomp` now narrows 32-bit work (`NARROW_EDITS` in the patch tool). A guest register is 64 bits wide, but most results are 32-bit values whose upper word only copies bit 31, and storing that copy took an extra instruction and an extra store. Per unit, the generator now tracks which registers' upper words are known to be such a copy, so `and`, `or`, `slt`, `move` (`daddu` with zero), `sd` and branch compares on them work in 32 bits. It also tracks which upper words nothing may read before they are rewritten, and skips storing those. Every exit from a unit (calls, returns, register jumps, time-slice checks) counts as reading every register, so guest state outside a unit is unchanged. `EERECOMP_WIDE=1` turns it off. Over the whole program, 116,000 of 451,000 32-bit results now skip the upper word, 64-bit register accesses fell from 411,000 to 344,000, and sample units are 2.1% smaller. If no exit read anything, 296,000 would skip it. Most of the rest are kept for calls. A version that solved liveness over the whole program, so a call kept only what its callee reads, reached only 123,000, because callees save registers with 64-bit stores and their returns read everything.    Hot copies (`tools/p3fes_eehot.py`, 2026-11-10). The translated game is about 300 very large functions with every guest register in memory. The tool writes a second copy of each busy game function as a small C++ function of its own, from the same generated text:
   - Guest registers are locals for the whole function, as two 32-bit halves.    - `eerecomp` puts a call to the copy at the top of the original code (a native named `hot_...`, the `HOT_EDITS` stage of the patch tool). The original stays, and anything that enters a function in the middle runs it.

   Waits on the game's core (2026-11-11). With pictures skipped, the lobby's core was busy for about 400 million cycles per 30 frames, about 500 ms of the 590 those frames took. Timers around every place the game thread sleeps found the rest:
    - The speed hold (`hold_speed` in `main3ds.cpp`) slept 45 ms in every 30 frames, though the lobby was slower than a PS2. A slow stretch used up its two frames of credit, and the faster frames after it then slept. Four frames of credit stop that.
    - The rest was the I/O processor: 45 to 70 ms per 30 frames, all of it in one place. After the game sends a SIF DMA, it waits for the I/O processor to catch up entirely if it runs out of work in the next 300,000 cycles, since it may be waiting for a reply. Now, after each vblank ends, the I/O processor may run ahead of the game's clock up to the next vblank (`iop_horizon` in `iop3ds.cpp`, `IOPAHEAD_EDITS` in the patch tool). ## Native model programs (`g3`)
The game's two RenderWare model programs on VU1, g3_generic (program 042) and g3_skin (064), take over half of the drawing core's time in 3D scenes. `g3native.cpp` and `g3model.cpp` compute their MSCNT batches in plain C++ from VU1 memory and the registers the program's init left, and send the same GIF packets. The program's own MSCAL start (its init and the object's first batch) always runs, and any batch the model does not cover runs the program. Settings in `args.txt`:

- `g3 1`: native. `g3 2`: the program draws, the model runs as well, and any packet or left-behind register that differs is logged as `[g3]` lines (the GS ignores the w word of STQ, which holds a leftover register value, so it is not compared). `g3 3`: like 2, and also saves `g3cap N` batches (one in `g3every K`) to `/p3fes/g3cap.bin`.
- `tools/g3check.cpp` runs the model on a Mac against a capture: `c++ -std=c++20 -O2 -ffp-contract=off -DG3_HOST_CHECK -Iport3ds tools/g3check.cpp port3ds/g3model.cpp -o build/g3check`, then `build/g3check g3cap.bin [-v N]`. The capture holds VU1 memory from your own disc, so keep it on your computer.
- Every float operation is done in the program's order with single roundings, so `g3model.cpp` is built with `-ffp-contract=off`.

Covered: the batch start's integer-to-float conversion, ambient and directional lights, the clamp to 255 and the material colour, morph off (other morph values leave the compiled program); g3_skin's four-bone weighted matrices, with the 5-qword input compacted to 4; the triangle strips with and without fog; and the full clipper's first pass when every vertex is beyond one same plane, which draws nothing and does not swap the output buffers but leaves vf28-30.z at w - w. Not covered yet: point and spot lights, the guard band clipper, the clipper's drawing (clip codes all inside, or real clipping), and triangle lists.

Checked on 2026-11-19: two 600-batch captures (lobby, battle) byte-identical in `g3check` (95% and 99% of batches covered); `g3 2` in Azahar found no difference in about 150,000 batches, and on the console none in about 127,000 battle batches; `g3 1` in Azahar gave pictures identical to `g3 0` (one lobby shot, 80 battle shots with `draw 3;shots 1`).

Speed on the console with every picture drawn (`draw 1`, ms per game frame, `g3 0` against `g3 1`): the first version, which went over the batch stage by stage like the program with five 1024-vertex arrays (76 KB against a 16 KB data cache) and built packets with a vector insert per qword, was slower (battle 47.4 to 49.9, lobby 96.6 to 105.1). Doing every stage for one vertex before the next, into a buffer kept between batches, made it a little faster (battle 47.1 to 46.3, lobby 96.4 to 93.8). The compiled programs are already close to plain C++, so the same arithmetic on the same core saves about 3%; the CPU-only model remains opt-in. The model is the exact reference for moving this work off the CPU (the renderer fed directly, or a PICA vertex shader).

### On the GPU's vertex shader (`g3 4`)

The standard renderer selects this path when its shader is available. Software rendering and split GS use the compiled programs by default. Set `g3 0` to use the compiled programs with the standard renderer.
`g3 4` hands each batch's own vertices to the GPU instead, and the vertex shader does the program's work: `g3::gpu_batch` (in `g3model.cpp`) reads the batch from VU1 memory into 48-byte vertices (position, uv, prelit colour, normal as signed bytes, four bone weights and their bones) plus the shader's inputs (vf28-vf31, vf02, fog factor, material, the ambient lights' sum, up to three directional lights, and a palette of 24 bones of 3 vectors each), and `pica::draw_g3` draws it as a GPU triangle strip (no indices, each vertex shaded once). Before that, the batch's own GIF tag goes through the GIF with NLOOP 0. That sets PRIM and does what the GIF does at every tag: Q goes back to 1, and texture uploads held back while PATH3 was masked are let through before the batch, as they would be before the program's packet. `gs.v.pica` has one program with two halves picked by the bool uniform `isg3`, so switching between the GS path and this one changes no shader. The g3 half blends the bone rows (only for g3_skin, a second bool `isskin`), transforms position and normal, projects through vf28-vf31 to the GS screen position (then on as the GS path does), lights the vertex (prelit + ambient + each directional light's colour times N.L clamped at 0, clamped to 255, times the material), and takes fog from w. The ADC culling the program does per triangle is the GPU's face culling: the GPU turns every other strip triangle round as (k-1, k-2, k), which is how the program's facing test alternates, and the y flip on the way to clip space makes the program's negative facing clockwise. Batches it does not take (what the model does not cover, more than 24 bones, more than three directional lights, colours or normals out of byte range, PRIM other than a Gouraud strip with ST, or the renderer on its own thread) go to the model as in `g3 1`. `g3gpu N` limits it for tests (1 generic, 2 skin, 4 lit batches, 8 no culling, 128 leave the batches out).

The pictures are close, not exact: the GPU's floats have 24 bits and it rasterises its own triangles. `build/g3check g3cap.bin -gpu` runs the shader's arithmetic in plain floats on the batches `gpu_batch` gives and compares it with the exact packets: both captures within 1/16 pixel, colour and fog within 1, and every triangle's culling the same (17,500 and 22,200 vertices). In Azahar `g3 4` against `g3 0` (`draw 3;shots 1`, 400 frames): lobby mean difference 0.1 per pixel (only scattered edge pixels), battle at most 0.12 over 82 shots. Location of a bool uniform: `shaderInstanceGetUniformLocation` gives b0 as 0x68, and `C3D_BoolUnifSet` takes the 0x68 off itself, so it gets the location unchanged.

The command list decides the speed. Each frame's GPU commands go into one fixed 1 MB buffer (`kCommandBuffer`, recorded by `gpuoverlap.cpp`), which only splits when 75% of what is left is used, so a frame must stay well under 1 MB; growing past its half makes the recorder wait for the previous frame's GPU work. The first version drew every batch on its own and sent all its uniforms: about 1.8 KB of commands per batch, 584 KB per battle frame (43 ms of waiting per frame, battle 47.3 to 55.9 ms) and over 1 MB in the lobby, which overran the buffer and took down the system's GPU service (`gsp` fatal error 0xF8A02BFE in `luma/errdisp.txt`). What fixed it:
- a uniform is written only when its value changes (`put_unif` against citro3d's copy), and each bone is 3 vectors (its matrix turned so x, y and z are each a dot product with (position, 1)), so 24 bones fit;
- bone slots follow the matrix itself, not its VU address (the game uploads each batch's bones wherever it likes), so a bone used by the batch before keeps its slot and is not sent again; about 2 uniform vectors per batch remain;
- consecutive g3 batches with the same state, uniforms, culling and bone slots are drawn as one strip, joined by degenerate triangles (with one more vertex when needed so each batch starts at an even place, where the GPU's alternating winding starts). A draw call costs about 150 command words and a framebuffer flush, so this matters most: battle draws per picture went from 425 to 150, lobby from about 700 to 283. A GS shape, a state change, or a batch needing different uniforms or a bone slot in use draws what waits;
- the g3 vertex layout, buffer, shader half and culling stay set across g3 draws, and a batch is handed back to the exact path if the frame's command list ever gets near full (none were, after the above).

Clipper batches (g3_generic with flags 0xB) go to the GPU too when no vertex is beyond the clipper's depth planes. What the clipper does was found from the program's output, not its code. A probe in `g3 2` logs, for each batch the model declines, the registers it changes and its GIF tags. `tools/g3check -clipstrip` compares its vertices with the plain strip's, and the captures were matched against each vertex's clip codes:
- It clips each triangle against a box: x and y within the guard band (M[0x3FD].x and M[0x3FE].x pixels from the centre, 325 by 229, which is the picture plus about 5 pixels), and depth from w = 150 to w = 10,000 (the M[0x3FD].z + M[0x3FE].z * w test). Triangles wholly outside one plane go, triangles crossing one get new vertices on it, and the pieces go out as strips joined by repeated vertices, with the same PRIM.
- A vertex that keeps its triangle is the plain strip's: same position, depth and colour, STQ within one unit in the last place, and the same ADC except on zero-area triangles. The clipper leaves the same registers a strip batch does (vi13 and vi14 swapped; vf28-30 z are already 0 at every batch start in the captures).

So with every vertex in front of the near plane and short of the far one, the whole strip drawn by the GPU gives the same pixels: its own edges cut where the guard band would. A batch with a vertex outside the depth range is declined as `clipper depth` and goes to the exact path. In the lobby that moved 2,000 of every 24,000 generic batches off the program (2,400 of 53,000 are left: 1,400 triangle lists and 1,000 past the depth planes); battle has none left. In Azahar against `g3 0`, the lobby mean difference went from 0.06 to 0.18 per pixel (sub-pixel floor edges at the top of the picture, 25 pixels over 30 in the worst shot) and the battle was unchanged at 0.07. On the console (same settings as below, one run each): battle 42.6 to 40.7 ms per game frame, lobby 80.0 to 77.7. Lobby commands grew to 402 KB per frame, still under the half of the buffer where waiting starts.

Triangle lists (g3_generic with flags 0xC, the blob shadows under the lobby's characters, PRIM 0x4B) go to the GPU as well. `tools/g3check -liststrip` shows their vertices are the plain strip's (colour and position the same; S is a NaN in both on some vertices, unused since these draw without a texture). The program's list code (042 from 0x1520) takes each triangle's facing from the cross product of its edges and sets ADC as the strip does for a triangle at an even place. All 24,000 list triangles in 400 lobby frames faced the side that is kept, so none showed a cull. `gpu_batch` rebuilds a list as one strip: a0 b0 c0, then c0 a1 a1 a1 b1 c1 and so on, so each triangle starts at an even place behind triangles with no area (2n - 3 vertices, hence `Gpu::v[512]`). One catch: lists send XYZF2 even without fog, so the GS takes their z word shifted down 4 bits. `Gpu::xyzf` gives the shader that scale (without it the shadows sat 16 times nearer and came out darker). Fog lists and g3_skin lists have not been seen and stay on the exact path. In Azahar the lobby is unchanged from the build before (0.001 per pixel). Texture uploads (2026-11-22). A profile of the drawing core in the lobby with every picture drawn put texture uploads first, at 15% of its time, and most of that was copying deferred uploads into GS memory that nothing would read. Two changes:

- `find_texture` checks a small texture (64 by 64 or less) against GS memory only when something other than the upload it came from has written its blocks since. Every block now keeps the start stamp of the upload that last wrote it (`g_block_upload`), and an upload that arrives in pieces keeps the stamp of the piece at the corner. Before, each piece looked like a new write, so the check ran and forced the deferred pages out almost every time.

### Converted-vertex cache (`g3cache`)

Most of what `g3 4` still costs the CPU is turning each batch into 48-byte vertices. The game sends most models by reference: the VIF unpacks of a batch read straight from PS2 RAM (`DirectStreams`), and the same model comes back every picture from the same addresses. `g3cache.cpp` converts such a batch once into the arena, 2 MB of GPU-visible memory (43,008 vertices, allocated in `pica.cpp` after the linear heap was raised to 15 MB). It then draws it from there for as long as the same streams come again, each batch on its own by vertex range (`C3D_DrawArrays`). An index list could join them into strips (the last index again, the first again, and a pad for even parity), but indexed drawing hangs the console's GPU (below), so that is only a test switch: `g3index 1` joins unskinned batches by index, `g3index 2` skinned ones too. A strip from the arena and one from the ring are drawn apart.

- The key is each stream's offset in PS2 RAM with its unpack format (positions, uvs, colours, plus normals when lit and weights when skinned), the vertex count and how the batch reads them. Batches with no key go the usual way: dual-context batches, lists, data in VU memory, over 256 vertices, or skin batches without their weights in RAM. A check build hashed the converted vertices of every batch: in the lobby, the lockers and the first battle, the same key always gave the same vertices (60 million vertices, no change). On every use a few words of positions and uvs are compared as a guard; a change counts as `stale` and converts again.
- A skinned entry also keeps which VU address went to which bone slot. On a hit the bones are read from those addresses again and put back into the same slots (`g3::restore_bones`), since its vertices name slots. If two addresses that shared a slot now differ, that use goes the usual way (`bones split`).
- Arena space comes from a pointer that goes round. An entry drawn in this picture or the one before stays (the GPU may still be reading it), so a live entry in the way is stepped over. After 8 steps the batch goes the usual way (`no room`).
- `g3cache 0` turns it off, `g3cache 2` logs counts every 600 frames. Skinned batches are cached too; `g3skin 0` leaves them out (see below for why they were off for a while). Per 600 frames in Azahar with `g3skin 1`: lobby 13.0 million vertices, 90% kept, 0.3% converted, 0.3% no room; battle 4.7 million, 89% kept (71% skinned), 0.1% converted; lockers 5.0 million, 95% kept. No scene showed a stale entry or a split bone. Without skinned batches (`g3skin 0`): lobby 37% kept, battle 18%.

In Azahar, pictures with the cache on and off are identical, pixel for pixel, in the lobby, the battle, the lockers, a movie and the level-up screen, with and without `g3skin 1`. The cold boot differs between two runs with it off as much as between on and off; the opening movie lands on different frames. On the console with every picture drawn (`draw 1;debug 32;stereo 0`, ms per 30 frames, 2026-11-22):

| | Cache off | Unskinned only | With `g3skin 1` |
|---|---|---|---|
| Lobby | 1127 | 1058 (−6%) | 972 (64.8 ms per picture, −14%) |
| Battle | 549 | 542 | GPU hangs at the first picture (drawn by index, before the fix below) |

### Lobby speed: the wait for the I/O processor (2026-11-25, evening)

**What cost time.** A sampling build that also notes the game's return address put 5.5% of the lobby's game thread (`draw 1`; 8.2% at `draw 3;uncapped 1`) under return address 0x005073F4, `WaitSema` in `sceSifCallRpc`: the game waiting for an I/O processor reply. About once in five vblanks the game sends a request right after a vblank, when the I/O processor still has most of a vblank of its own work (3.2 million cycles on average) to catch up on, and the runtime waited until the two clocks were level. That was 4 to 17 ms each time and 28 to 42 ms per 30 vblanks, nearly all of the 42 ms known before. Taking the wait out had been tried and made the game drop pictures, because the game does need the reply.

**Fix.** The wait ends as soon as the I/O processor has sent the game a packet (`sif::reply_ready`, `iop_wait(enough)` in `iop3ds.cpp`, `idle()` in `system.cpp`; all in the patch tool). It does the rest of its backlog on core 1 while the game draws, so replies reach the game earlier than on a PS2, as they already could with `iop_horizon`. Waits are now 2 to 4 ms per 30 vblanks. `iopthread 0` is not affected.

### Steady picture rate, and how close to full speed (2026-11-25, later still)

**Cause of the swings.** In the stereo battle and office the automatic skipping swung between 5 and 16 pictures/s. The drawing queue hides several pictures, so a short try at "draw everything" looked on time. The game then fell behind, the skip rose once for each picture that found the queue still full, and it took 10 to 15 s to come back down. The good try had also halved the wait before the next one.

**Fix** (`PicturePacing` and `choose_next_picture()` in `pica.cpp`):

- A lower skip counts as good only after 12 rounds. If it falls behind before that, the skip goes back by one step, and the next try waits twice as long.
- A try also fails when the drawing thread has almost nothing left over (under 1/32 of the time) in its second half.
- After a raise because of a full queue, the next raise waits 12 pictures, unless the game does little but wait. A game that is at most 10% late raises the skip by one step.
- New level: draw two of three pictures (draw, draw, skip). It averages 20 a second and still draws into both frame buffers. Before, the first step down from 30 was 15.

### Faculty office blinking: cause and fix (2026-11-25)

**Symptom.** In the faculty office the floor disappears for single pictures (black shows through), and so do single letters of the dialogue ("h", "--") and, once, a strip of wall.

**Cause.** `apply_state()` in `pica.cpp` draws from an old render target instead of the texture the game has just uploaded. When a texture's address (TBP) is page-aligned and some `Target` has the same page as its FBP, that target is used as the texture (`source`, "Drawing with a picture that was rendered earlier"). It checks only the address. Nothing drops a target, or marks it old, when the game uploads a texture over that memory: `note_transfer()` does not look at targets, and a target goes only when all 8 slots are in use. The code has been like this since the port's first commit (0e578a9).

In the lobby and the hallway the game draws a scratch picture at page 504 (block 16128, 128 wide) and reads it back as a 128x128 32-bit texture. The office does not draw it, but uses that memory for ordinary textures, and RenderWare moves those around GS memory from picture to picture. Whatever lands on block 16128 is drawn with the hallway's old scratch picture. That is why a different texture blinks each time, why only one picture at a time, and why it depends on having walked in from the hallway.

**Proof on the console** (a build that only adds a log line at `source`, default settings plus `stats 1`, slot 1 in the lobby, walked to the office, "Let's see... In 1999..." line, 19 consecutive drawn pictures):

| Pictures | Drawn from the old target at page 504 (last drawn at picture 783, about 700 pictures before) | Seen |
| --- | --- | --- |
| 55596, 55686, 55866 | 4-bit 128x128 `BCB140CF` and 4-bit 32x32 `A23BA8B1` | floor and "--" missing |
| 55704, 55884 | 4-bit 32x32 `A75C20DB` | "h" of "Teacher" missing |
| 55578, 55668, 55758, 55848 | 8-bit 128x128 `FE0D7A9C`, 5 times | nothing visible, either eye |
| 55776 | 4-bit 32x32 `F1EA57BD`, twice | both "o" of "ago? Your" missing |
| the other 9 | none | correct |

Over 699 drawn office pictures of that run, 357 (51%) used the old target for something and 77 (11%) for the floor. The unchanged build showed the same faults in the same scene: 2 of 16 pictures without the floor, 2 without the "h".

**Why the counters missed it.** Nothing is missing or stale by their measure: `missing` 0, `decoded` 0, shapes constant (922), no `[stale]`. The only trace is in `stats 1`: `changes` minus `reused` is 7 in every full office picture when it is right, and more when it blinks. `slot2.state` hides the fault completely (10 of 10 pictures right in this check, and the difference always 7), because a loaded state starts with no targets. So the earlier check of the office from `slot2.state` could not see it. The "Faculty office disappearing floor" fixes above were for other faults.

**Not the cause:** running out of texture memory (271 KB free in the session where it was first seen, but it blinks the same with 1355 KB free and nothing decoded), remembered DMA chains, the vertex cache and the split command list (0 splits).

**Fix.** Each `Target` keeps the value of `g_stamp` at its last draw (`draw_stamp`, set by `note_drawn()`), and it is used as `source` only if that is not older than the newest upload to the texture's first block (`g_block_stamp[tbp]`). Otherwise `find_texture` gives the uploaded texture. Testing only "was anything uploaded here" is wrong: in the lobby and hallway the scratch picture was read 754 times, correctly, at an address that also had an older upload. `stats 1` counts "old targets passed over" for each picture.

**Checked on the console** with the same walk from the lobby into the office and the same dialogue line, 3D slider up: 35 of 35 screenshots (2 builds) right, and `changes` minus `reused` was 7 in all 600 pictures looked at. Old targets were passed over in 225 of 400 office pictures, and almost never in the lobby and hallway, where the scratch picture is still used. In Azahar the walk, level-up, movie, c21 and c22 scenes match the build before to within a few pixels, which come from the clipper change. Check this with the walk, not with a state saved inside the office.

## Testing
`route.txt` holds the button presses from a cold boot to the first battle, one `frame:button[:frames]` per line, for `ps2run --press`. It is timed for the Mac build: a 3DS cold boot drifts from it by hundreds of frames, so to reach a later scene on the 3DS, make a saved state on the Mac and load it.

Saved states from the Mac build load here, which skips the long opening: make one with `ps2run --save-state FRAME:file`, copy it to `/p3fes/`, and add `load file` to `args.txt`. `record sdmc:/p3fes/vu1` saves any vector programs that are not compiled yet: copy them to `games/p3fes/vu1` and run `vurecomp` again. `soft 1` draws with the software renderer, which is the reference when the GPU picture looks wrong.

- The test build logs to `/p3fes/log.txt`, so a run can be checked without looking at the emulator window. An uncaught C++ exception is logged there with its thread, then stops the program. In Azahar that shows up as CPU use falling to almost nothing.
- Always test from a cold boot as well as from a saved state. The out-of-memory stop at frame 1802 never appeared in the lobby, and a movie with no picture, because menu textures had split up the free memory, looked fine from a state.
- In the `[pica] frame` lines each number comes before its label: `9 reused 1 missing` means one texture could not be made, so its shape was left out. Any `missing` above 0 is a fault.
- `tests/test_3ds_natives.py` only checks that the list and the code agree. To compare a native routine with the game's own code, build a Mac copy that calls both and compares their output: the C paths in `native3ds.cpp` are written to run there too. The two small ARM instruction paths can only be checked in the 3DS build. To do the same with floating point, cut the routine's text out of `generated/p3fes`, compile it with `-D__3DS__ -ffp-contract=off` next to `native3ds.cpp`, set the ARM64 FPCR to flush denormals, default NaN and round to zero, and compare memory, registers and the budget on random input, overlapping pointers included. The animation and matrix routines had no difference in about 17 million cases.
- To check the ADX decoders on the 3DS or in Azahar, add `#define PS2_CHECK_NATIVES` before the first `#include` in `native3ds.cpp`, and translate the game with a copy of `natives.txt` that also lists `0053A5C0 loop_adx_frames_check` and `0053ACD4 loop_adx_stereo_check`, the last block of each decoder. Each native then works out what the game's code should leave and lets that code run, and the hook compares output, history, key, return value and instruction charge, and writes `[check]` lines to the log. Do not ship that build.
- Remove the define and translate the game again with the normal list before building for the console.
- `hide A-B` in `args.txt` leaves out batches of each picture, and `dump N` numbers them, which finds the shape behind a wrong pixel. Textures move around GS memory every frame here, so an address does not identify one for long.
- Before calling a difference from the Mac build a fault, compare over a few seconds. The Velvet Room's bright light is an animation with a 150-frame cycle, and the two builds were simply caught at different moments.
- For a comparison with skipping on, use `shots 2;draw 3`, not `draw 4`. An even `draw` skips an odd number of pictures, so only one of the game's two frame buffers is drawn, and in the lobby every shot is black. Check the pictures have content before believing a match.
- With the default picture skipping, `shots N` only catches a picture that was drawn. Use `draw 1` for comparisons, but also run scenes with skipping on: the frozen second buffer only showed up that way, and it looked just like a loading hang. `debug 4` skips the drawing but still runs the vector programs.
- A run that ends without a crash proves little. Look at the shots along the way: a frozen picture and a slow hang both pass as a clean run.
- Timing a whole-program run with `stats 1` is fair, but keep the counters away from anything called per shape: in Azahar one `svcGetSystemTick` costs about 450 ticks, which once hid inside the draw figures.
- The first shot or two of a run can come out black. That is the capture, not the picture: the same frame is fine later in a run.
- Azahar ignores a setting whose `key\default=true` line is still there, so test scripts must change both lines.
- A normal quit signal did not close Azahar here (probably its `confirmClose` prompt), so make sure test scripts leave no copies running: several copies share one log and SD folder.
